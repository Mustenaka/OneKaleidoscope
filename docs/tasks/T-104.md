# T-104: 让 `LiveControl` 可达，否则手机永远只读（D-B1）

> 状态：**已完成（2026-08-09）**。[T-103](T-103.md) 已通过。
> 里程碑：[MILESTONES](../MILESTONES.md) R3 硬前置之一
>
> 本轮由用户以项目主管身份批准直接推进；语义方案 A 已按
> [ADR-0019](../adr/0019-live-control-runtime-acceptance.md) 接受。实现与验收见
> [T-104-result](../gates/T-104-result.md)。

一句话目标：让 `LiveBinding::Controlling` 在真实控制发生时**能够到达**。

---

## 1. 问题

主管在 T-100 阶段 B 评审时发现（实现方未报告）：

`Capability::LiveControl` 在 `crates/kaleido-adapter/src/capability.rs` 里
**只出现在 `ALL_CAPABILITIES` 枚举列表中，没有任何代码路径会把它标记为 proven**。

而 [PROTOCOL](../PROTOCOL.md) §4.3 规定：

> `Controlling` 要求同时具备 `LiveObserve` 与 `LiveControl`。

所以 `LiveBinding::Controlling` **结构性不可达**。

但 T-100 阶段 B 的真实运行里，broker 确实通过这条 live 连接**提交了 prompt、
回答了审批，runtime 都接受了**——按任何合理理解，那就是控制。真实投影里：

```text
live_observe    supported      observed_in_traffic
turn_prompt     supported      observed_in_traffic
live_control    not_verified   absent               ← 明明控制了，却说没验证
```

**这不是 T-100 的不通过项**（方向是「少说」不是「多说」，DoD 也没要求 `Controlling`），
但它是 R3 的真问题：**手机要靠 `LiveBinding::Controlling` 判断「我现在能不能干预」。
不解决，手机会一直渲染成只读。**

## 2. 这张卡首先要回答一个语义问题

在写任何代码之前，先回答：**`LiveControl` 到底是什么，它和 `TurnPrompt` /
`InteractionApproval` 有什么区别？**

至少有两种可信读法，必须选一种并写进协议：

| 读法 | 含义 | 后果 |
|---|---|---|
| A：`LiveControl` = 「能对这条 live 连接发出任何改变状态的命令」 | 是 `TurnPrompt` / `InteractionApproval` 等的上位概括 | 一旦有任一控制类命令被 runtime 接受，就该 proven |
| B：`LiveControl` = 「能控制一个**不是自己创建**的会话」 | 针对 `shared_runtime` / `external_native` 的附着控制 | `broker_managed` 会话天然不需要它，那 `Controlling` 对 R2 就不适用，需要另外说明手机怎么判断可干预 |

现有协议文本没有把这一点写清楚——这是主管的缺口。
**ADR 的核心工作就是做这个决定并写进 §4.2 / §4.3。**

如果选 B，还必须回答：R3 的手机应该看什么字段来决定是否显示干预按钮？
不能留下「协议自洽但手机没法用」的结果。

## 5. Definition of Done

- [x] ADR 已获主管批准，且**先于**代码改动；
- [x] `LiveControl` 有真实可达的证据路径，且该路径**只在真的控制发生后**才成立；
- [x] **replay 路径仍然到不了 `Controlling`** —— 录制证明协议形状，不证明现在能控制。
      这条是硬要求，有测试；
- [x] **没有证据时到不了** —— 一个测试证明：仅有 `live_observe` 时 `Controlling` 被拒；
- [x] 真实验收：用 T-100 已有的 `slice run` 跑一次真实 Codex 会话，
      给出 `SessionIndexView` / `RuntimeCapabilityView` 的实际 JSON，
      证明 `live_control` 与 `LiveBinding` 的取值符合 ADR 的定义；
- [x] `turn_steer` **仍然**是 `not_verified` —— 不许被这次改动顺带提升；
- [x] 至少三处「改坏 → 变红」，其中必须包含：没有 runtime 接受证据就提升 `LiveControl`；
- [x] `cargo xtask ci` exit 0，三平台 CI 全绿。

## 6. 边界

**禁止**：

- 改 `docs/REQUIREMENTS.md`、`docs/ARCHITECTURE.md`；
- 改 `schemas/**`、`tests/fixtures/**`、`spikes/**`；
- 顺手动 P-1（[T-103](T-103.md) 已处理）或 D-B2 / D-B6 / D-B7 / D-B8 / D-B11；
- 扩大到 workflow、transport、移动端、其他 provider。

**最容易翻车的地方**：为了让 `Controlling` 可达而放宽 `LiveBinding::validate_against`
或 `EvidenceSource` 的判定。那样等于用「让它能到达」替换「证明它该到达」，
是本项目最严重的一类违规。正确做法是**先定义清楚什么算证据，再让证据真的被观察到**。
