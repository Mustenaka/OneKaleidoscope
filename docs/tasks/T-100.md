# T-100: Codex Broker 管理会话的本地纵切

> 状态：**active，2026-07-30 由项目主管下发。** R1 已按 [ADR-0013](../adr/0013-platform-track-order.md)
> 有条件通过（Swift 编译作为 UB-R1-S 携带至 R8，见 [T-102](T-102.md)），本卡不再 blocked。
> 里程碑：[MILESTONES](../MILESTONES.md) R2
> 实现方：Codex。主管：Claude Code。
>
> **本卡分两阶段交付，中途有一次强制评审。见 §5.0。**

一句话目标：完成唯一纵切 `Codex app-server → ADR-0012 钉定路径 decoder →
reducer → canonical state → durable log → Rust diagnostic client`，并证明重放恢复。

这张卡**只做一个 provider、只做本机、没有传输层、没有移动端**。

## 2. 用户可见结果

本卡完成后，负责人在自己的终端可以做到：

1. 让 hostd 启动并拥有一个真实 Codex app-server 会话，看到 `SessionIndexView` 里
   出现该会话，`ownership = broker_managed`，`live_binding = observing`；
2. 从诊断客户端发一条 prompt，实时看到 `LiveActivityView` 的流式增量，
   最终在 `TranscriptView` 看到完整 turn 的全部 item；
3. 触发一次文件修改审批，在 `AttentionInboxView` 看到它（含 join 状态），
   分别用 accept 和 decline 决定它，并看到两种结果的差别；
4. 往队列里放一条 steer 意图的输入，看到它**明确显示为排队**，
   并在 `RuntimeCapabilityView` 看到 `turn_steer` 不是 `supported` 及其原因；
5. 杀掉 hostd 再启动，从 durable log 重建出同一份 canonical state。

这五条就是移动端将来要显示的东西，只是这一步用 JSON 输出代替 UI。

## 3. 产出

新建四个 crate，全部在 `crates/` 下。每个都必须同时登记进根 `Cargo.toml` 的
`members` 与 [`docs/dependency-rules.toml`](../dependency-rules.toml)（`kaleido-state` 的规则条目主管已预先写好）。

> `cargo xtask check-deps` 用自己的 TOML 读取器解析 `crates/*/Cargo.toml`，
> **不支持点号键**。`[package]` 里必须写 `edition = { workspace = true }`，
> 不要写 `edition.workspace = true`。参照 `crates/kaleido-proto/Cargo.toml`。

### 3.1 `crates/kaleido-state`

依赖：`kaleido-proto`（外加 `serde`/`serde_json`/`thiserror`/`tracing`，IO 用 `std`）。

- `apply(effect) -> Result<Vec<LogRecord>, StateError>`：校验 → 分配 cursor → 追加日志 → 更新内存投影；
- 追加式 durable log：每个 `StreamKey` 一个文件，一行一条 `LogRecord` 的 JSON；
- `load(dir)`：读回日志、`verify_contiguous`、重建内存状态；
- `snapshot(session_id) -> SessionSnapshot`，且 `SessionSnapshot::validate()` 通过；
- 六个投影的纯函数导出（见 §4）；
- 幂等：同一 `(actor, idempotency_key)` 第二次返回 `CommandOutcome::Duplicate`，
  且不产生新的 `LogRecord`；
- 内容寻址存储：`ContentRef` 的正文按 `content_id` 落在独立目录，日志里只有引用。

### 3.2 `crates/kaleido-adapter`

依赖：`kaleido-proto`。只放 provider 中立的 trait 与类型：

- `trait ProviderRuntimeSession`：`start`、`submit_prompt`、`respond_attention`、
  `close`，以及一个产出 `StateEffect` 的接收端；
- 能力探测结果类型；
- 连接生命周期错误类型。

**不得**在这里出现任何 Codex 概念。

### 3.3 `crates/kaleido-adapter-codex`

依赖：`kaleido-proto`、`kaleido-adapter`（外加 `tokio`、`serde_json`、`thiserror`、`tracing`）。

- 以子进程方式启动 `codex app-server`，走 stdio 双向 JSON-RPC；
  Windows 上子进程必须 `CREATE_NO_WINDOW`，退出时杀整个进程树；
- `surface.rs`：ADR-0012 D-2 要求的钉定路径表，每条含
  canonical 用途、上游 method、JSON Pointer、`required-surface.toml` 的 `entries.id`；
- `decode.rs`：只按该表读值，立刻转成 canonical 类型。未定型 JSON 不得离开本 crate；
- `reduce.rs`：按 [PROTOCOL.md §11.1](../PROTOCOL.md) 映射表产出 `StateEffect`；
- 服务端请求 ID 与客户端请求 ID 是**两个独立 ID 空间**（fixture 里客户端用 1/2/3，
  服务端审批请求用 0），必须分开管理；
- 审批：**只建模 `item/fileChange/requestApproval` 一族** → `AttentionUpserted`，
  join 用 `params.itemId`；回复用 `{"decision":"accept"}` / `{"decision":"decline"}`。
  `commandExecution` 与 `permissions` 两族的**回复合同不同构**
  （前者是不同构的 `oneOf`，后者 required 是 `permissions` 而没有 `decision`），
  按 [ADR-0014](../adr/0014-codex-approval-families-and-timestamp-units.md) D-1
  归入 `UnknownUpstreamMessage`，不得渲染成审批项。
  *（本条为 2026-07-31 修正：原文写「三个 method 同上」，是主管未核对回复 schema 的纸面推断。）*
- 时间戳：`turn/*` 的 `startedAt` / `completedAt` 是 **Unix 秒**，必须 ×1000；
  item 与审批的 `*Ms` 字段本来就是毫秒。见 ADR-0014 D-2。

### 3.4 `crates/kaleido-hostd`

依赖：`kaleido-proto`、`kaleido-state`、`kaleido-adapter`、`kaleido-adapter-codex`。
组合根 + 诊断客户端，一个二进制三个子命令：

```
kaleido-hostd slice run    --executable <codex.exe> --project-root <dir>
                           --log-dir <dir> --prompt <text>
                           [--decide-first-approval accept|decline]
                           [--enqueue-steer <text>] [--timeout-secs 120]
kaleido-hostd slice replay --fixture <path.jsonl> --log-dir <dir>
kaleido-hostd slice show   --log-dir <dir> --projection <name> [--session <id>]
```

`show` 的 `--projection` 取值即 §4 的六个名字，输出为格式化 JSON。
`replay` 用同一套 decoder / reducer / store 处理已录制 fixture，**不启动任何进程**。

## 5. Definition of Done

### 5.0 两阶段交付与强制中途评审

上一轮 M1 的失败模式是：一张大卡闷头做很久，等到交付时才发现方向已经偏了。
本卡因此拆成两个阶段，**阶段 A 完成后必须停下来交付一次**，等主管评审通过再做阶段 B。

| 阶段 | 内容 | 对应 DoD | 依赖真实 Codex 进程 |
|---|---|---|---|
| **A（离线）** | 四个 crate 骨架 + fixture 驱动的 decoder/reducer/state/日志/投影 + `slice replay` + `slice show` | §5.1 前三条、§5.2 全部、**§5.4 第一、二、四条**、§5.5、§5.6、§5.7、§5.8、§5.9 | 否 |
| **B（真实进程）** | `slice run` 接真实 `codex app-server` | §5.1 第四条、§5.3、**§5.4 第三条**（进程提前退出）、§6 真实验收 | 是 |

*（§5.4 的分配为 2026-07-31 修正：原文写「A = 后两条、B = 第三条」，四条里第一、二条
两边都没分到，且第三条被重复分配。现按可执行的读法固定为上表。）*

规则：

- 阶段 A **必须**先做完并单独交付一次报告（格式同 §8）。没有阶段 A 的绿，不许开始阶段 B；
- 阶段 A 的所有 DoD 都是**确定性**的：只依赖已提交 fixture，不依赖登录、网络或本机 Codex 版本。
  因此阶段 A **不允许**出现任何「因环境原因未取得证据」的格子；
- 阶段 B 若被真实 Codex 的登录/网络/版本问题阻塞，按 §6.4 处理：阶段 A 的成果不受影响，
  阻塞单独登记，不得回头放宽阶段 A 的断言来「凑绿」。

## 6. 真实验收（人工执行，负责人在自己的终端）

### 6.1 环境

Codex 精确版本 `0.146.0`（`codex-cli 0.146.0`），与 `schemas/codex` 快照一致。
若本机 Codex 已升级，**先** `cargo xtask schema diff`，有漂移就停下来报告，
不要拿新二进制对着旧快照跑。

工作目录**不要**用 `tests/fixtures/sandbox`。新建一个一次性目录，例如
`target/t100-scratch/`，放一个 `editable.txt`（内容 `ORIGINAL`）。

### 6.2 三次运行

`thread/start` 参数按 fixture 已验证的组合：审批场景用
`approvalPolicy = on-request` 且 `sandbox = read-only`（这是 03/04 两份 fixture
实际产生审批请求的配置）；纯文本场景可用 `sandbox = workspace-write`。

```powershell
$codex = "<绝对路径>\codex.exe"
$scratch = "target\t100-scratch"
$log = "target\t100-log"

# 1) 纯文本 turn
cargo run -p kaleido-hostd -- slice run --executable $codex --project-root $scratch `
  --log-dir "$log\a" --prompt "Reply with exactly this plain text and do not use any tool: KALEIDO T100"

# 2) 审批 -> accept，并同时放一条 steer 意图输入
cargo run -p kaleido-hostd -- slice run --executable $codex --project-root $scratch `
  --log-dir "$log\b" --decide-first-approval accept --enqueue-steer "please also mention DONE" `
  --prompt "Use the file-editing tool to replace the complete contents of editable.txt with exactly KALEIDO T100 PROBE. Do not run a shell command."

# 3) 同一 prompt -> decline
#    先把 editable.txt 恢复为 ORIGINAL，否则运行 2 已经改完文件，
#    Codex 会判断「无需修改」而不再发出审批请求，这一格就取不到 decline 证据。
Set-Content -Path "$scratch\editable.txt" -Value "ORIGINAL" -NoNewline -Encoding utf8
cargo run -p kaleido-hostd -- slice run --executable $codex --project-root $scratch `
  --log-dir "$log\c" --decide-first-approval decline `
  --prompt "Use the file-editing tool to replace the complete contents of editable.txt with exactly KALEIDO T100 PROBE. Do not run a shell command."

# 4) 重启后重建（六个投影一起看）
cargo run -p kaleido-hostd -- slice show --log-dir "$log\c" --projection all
```

*（第 3 步的恢复动作与第 4 步的 `all` 为 2026-07-31 修正：原文漏了恢复步骤，
且第 4 步只看 transcript，与 §6.3 要求的六个投影证据不一致。两处都是实现方在阶段 B
实际执行时发现的。）*

### 6.3 每次运行要留的证据

- Codex `--version` 输出；
- 六个投影各一份 JSON（脱敏后可直接贴）；
- 运行 2 与运行 3 的 `fileChange` item 状态差异（`completed` vs `declined`）
  与两者 `Turn.status` 均为 `completed`；
- 运行 2 中 steer 条目始终 `pending`；
- 运行 4 与运行 3 结束时投影相同。

### 6.4 允许的失败

如果真实 Codex 在本机因登录或网络不可用而无法完成 turn（历史上出现过），
**replay 路径的全部 DoD 仍然必须绿**，然后按 `CLAUDE.md` §7 的格式登记阻塞，
并明确写出哪几格 DoD 因此未取得一手证据。不要为了凑绿去伪造运行结果。
