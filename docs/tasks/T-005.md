## 背景

你在 T-003 的阻塞报告中证明了两件事：

- progenitor `0.14.0` 只支持 OpenAPI 3.0.x，无法解析 OpenCode `1.18.8` 的 3.1.0 spec（`exclusiveMinimum` 数值 vs 布尔）
- typify `0.7.0` 无法解析 Codex `0.144.6` schema 的嵌套 `definitions`，仅取 v2 子集会丢掉 69 个 v1 定义，其中 `ServerRequest`、审批请求、`Elicitation`、`JSONRPCMessage` 全是我们必须要的

**这份报告是对的，处置方式也是对的。** 主管据此签发了 ADR-0005：

- 「类型不许手写」的铁律**保留**
- 允许在 schema 与生成器之间插入受纪律约束的**规范化层**
- `typify` / `progenitor` 从「必须使用」降级为「首选候选」
- **本卡的任务是拿证据做选择，而不是让钦定的工具跑通**

## 执行顺序（按此顺序做，不要跳步）

### 第 0 步：先补一份缺失的证据

你在阻塞报告里提到「单独生成官方 `ServerRequest.json` 同样触发 typify 的未实现分支」，但**没给出那个分支的具体错误**。

**先把它补上**：完整 panic 消息 + `RUST_BACKTRACE=1` 的关键帧 + 触发它的 schema 片段。

这条决定了后续走向 —— 如果 typify 的问题只是嵌套 `definitions`，规范化层就能解决；如果它对 `ServerRequest` 这类结构本身就不支持，那规范化层再怎么写也没用，必须换工具。**不要跳过这一步直接开写规则。**

### 第 1 步：Codex 链 —— 先试规范化 + typify

按 ADR-0005 D-2 的纪律实现规范化规则。已知至少需要一条：

| 规则名 | 变换 |
|---|---|
| `hoist_nested_definitions` | 把 `#/definitions/v2/Foo` 提升为顶层 `#/definitions/v2_Foo`，并重写全部指向它的 `$ref`。**命名必须无碰撞**，碰撞时报错而不是覆盖 |

其余规则按实测需要添加。**每加一条都要问自己：这是纯机械变换吗？有没有在猜语义？**

**硬性上限：规则数超过 10 条即停止**，按 `AGENTS.md §5` 报告，转第 3 步。

### 第 2 步：OpenCode 链 —— 两条路都要评估，不许只试一条

| 路线 | 做法 |
|---|---|
| **路线 A** | 写 3.1 → 3.0 降级规则（`exclusiveMinimum`/`exclusiveMaximum` 数值→布尔+`minimum`/`maximum`、`type: [T,"null"]`→`nullable`、`const`→单元素 `enum` 等），再喂 progenitor |
| **路线 B** | 改用原生支持 3.1 的生成器。已知候选：`openapi-to-rust`（crates.io，MIT，声称支持 3.0.x/3.1.x，**且内建 SSE 客户端**）。**注意其成熟度存疑：pre-1.0、star 数很低、官方声明「1.0 前 minor 版本可能改变生成的 Rust API」** |

**两条都要跑到能给出结论为止**，把证据填进 `docs/gates/T-005-evidence.md`。

> **额外考量（评估时要一并回答）**：progenitor 只生成 REST 客户端，**不处理 SSE**。
> 而 OpenCode 的 `GET /event` SSE 流是我们的主数据通路，REST 反而是次要的。
> 路线 A 意味着 SSE 那一半无论如何要另行处理。请在证据表里明确回答：
> 走路线 A 的话，SSE 侧的类型从哪来？（提示：事件 payload 的类型定义本身在 spec 里，
> 缺的只是传输层框架 —— 那部分属于传输管道，不属于「手写类型」，不违反 §3.2）

### 第 3 步：填证据表并给出建议

`docs/gates/T-005-evidence.md` 必须逐项填：

| 项 | Codex 链 | OpenCode 路线 A | OpenCode 路线 B |
|---|---|---|---|
| 是否生成成功 | | | |
| 生成物 `cargo check` 是否通过 | | | |
| 规范化规则数量 | | | |
| 规则中是否有非纯机械变换 | | | |
| 覆盖到的定义数 / 总数 | | | |
| **12 个 UACP 事件变体所需类型是否全部覆盖** | | | |
| 工具版本 / 维护状况 / 许可证 | | | |
| 生成物能否反序列化 T-004 的真实 fixture | | | |
| 你的建议与理由 | | | |

**最后一行不要客气，直说你倾向哪条以及为什么。** 主管要的是有依据的判断，不是并列陈述。

### 第 4 步：交叉验证（本卡最有价值的一步）

用生成出来的类型**反序列化 T-004 录制的真实报文**。

```
tests/fixtures/**/*.jsonl 的每一条 payload
        ↓  serde 反序列化为生成的类型
        ↓  再序列化回 JSON
        ↓  与原始 payload 做语义比较（键顺序无关）
必须完全一致
```

**这是判断生成链是否真的可用的唯一硬标准。** 能编译不代表能用——字段可选性错了、枚举变体缺了、`untagged` 用错了，都只有拿真实报文喂进去才会暴露。

失败的条目必须逐条列出：哪个文件哪一行、哪个类型、差异在哪。**不许通过放宽类型（改成 `serde_json::Value`）来让它通过** —— 那等于放弃类型安全。

## 允许的结论包括「做不到」

如果结论是「Codex 链在当前工具生态下无法自动生成完整类型」，**这是一个合格的交付**，只要证据充分。

主管会据此另开 ADR 决定：换工具、缩小子集、还是接受人工维护 + 漂移告警的妥协。

**不合格的交付是**：为了让 DoD 打勾而放宽类型、删定义、把生成不了的东西悄悄移出子集、或改用 `serde_json::Value` 蒙混过关。
