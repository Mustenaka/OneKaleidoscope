# T-102: 解除 UB-R1-S，并把 UniFFI 探针扩展到移动端真正需要的调用面

> 状态：**queued（可与 [T-100](T-100.md) 并行下发给第二个实现方；单实现方时排在 T-100 之后）**
> **硬约束：必须在 R3（Android 纵切）开工前完成。**
> 里程碑：[MILESTONES](../MILESTONES.md) R1 携带项 UB-R1-S + R3 前置
> 依据：[ADR-0013](../adr/0013-platform-track-order.md) D-3 / D-4
> 实现方：Codex。主管：Claude Code。

一句话目标：用 macOS CI 取得 Swift 编译的真实机器证据，并把 UniFFI 探针从
「值类型能否表达」扩展到「**移动端订阅与命令回路**能否表达」。

这张卡**不写任何产品逻辑、不建 Android/iOS 工程、不碰 `kaleido-proto`**。

---

## 1. 为什么需要这张卡

R1 的探针只验证了一件事：canonical **数据类型**能被 Kotlin/Swift 生成与（Kotlin）编译。
它是一个同步函数：

```rust
pub fn binding_probe(
    _command: CommandEnvelope,
    projection: ProjectionEnvelope,
    _error: Option<CanonicalError>,
    _effects: Vec<StateEffect>,
) -> ProjectionEnvelope
```

但 R3 的 Android App 实际需要的是三样**探针没有覆盖**的东西：

1. **投影被推送到移动端**（`LiveActivityView` 的流式增量、`AttentionInboxView` 的新审批）
   —— 跨 FFI 边界的回调接口或 async stream；
2. **命令返回可失败结果** —— Kotlin/Swift 侧看到的是抛出异常还是 sealed result；
3. **移动端主动订阅/退订**，并在进程被杀后重建 —— 带状态的对象（UniFFI interface）。

这三样如果 UniFFI 表达不了或表达得很别扭，改的是 [ARCHITECTURE](../ARCHITECTURE.md) §9
的模块边界，不是改 UI。**现在花半天知道，比 R3 写到一半知道便宜得多。**

## 4. 产出

### 4.1 `crates/kaleido-core` 的探针扩展

在现有 façade 上增加以下导出，**全部不含业务逻辑**，只为让两端编译器检查形状：

- 一个 **UniFFI callback interface**（外语言实现、Rust 调用），签名至少接收
  `ProjectionEnvelope` 和 `CanonicalError`，用于模拟投影推送；
- 一个 **UniFFI object**（带 `new` 与至少两个方法），其中一个方法接受上述 callback
  完成「订阅」，另一个完成「退订」，用于模拟带状态的订阅句柄；
- 一个 **可失败导出函数**，错误类型是 `CanonicalError`（或以其为载荷的 UniFFI error），
  用于确认命令失败在 Kotlin/Swift 侧是什么形态；
- 一个 **`async` 导出函数**，返回 `CommandAck`，用于确认 async 支持是否可用。

以上每一项如果 UniFFI 支持不了，**不要改 `kaleido-proto` 去迁就**：按 §7 报告。

### 4.2 Kotlin 与 Swift 消费探针同步扩展

- `crates/kaleido-core/bindings/kotlin-probe/src/main/kotlin/Probe.kt`：
  实现该 callback interface，创建订阅对象，调用可失败函数并处理异常，
  在协程里 await async 函数；
- `crates/kaleido-core/bindings/swift-probe/Probe.swift`：同样四件事的 Swift 版本。

两侧都必须**真的调用**新导出，不能只 import。

### 4.3 CI 集成

- `.github/workflows/ci.yml` 增加一步，只在 `matrix.os == 'macos-latest'` 执行：
  构建 `kaleido-core` cdylib → 生成 Swift 绑定 → 用 `swiftc` 编译两份生成源
  与 `Probe.swift`；
- 该步骤**不得**带 `continue-on-error`、`|| true`、`if: false` 或任何软化开关；
- Kotlin 探针的编译也一并进 CI（放在哪个 os 由实现方决定并说明理由），
  避免它继续只有本机证据。

### 4.4 文档

- `docs/DEVELOPMENT.md`：更新绑定生成/编译章节，写清两端探针现在覆盖哪四类调用面；
- `docs/gates/T-102-evidence.md`：工具精确版本、命令、**原始输出**、CI run 链接与 commit SHA。

## 5.4 已授权的窄边界例外：跨平台构建修复（2026-07-31 主管批准）

本仓库此前从未推送，因此 macOS / Ubuntu CI 是第一次真正运行。实现方在第一次真跑时
被冻结区的一处跨平台 lint 挡住：

```text
error: unused import: `validate_exact_permission_cwd`
--> spikes/kaleido-recorder/src/agents/mod.rs:407:9
```

主管已核实：该函数唯一使用点在同文件 `:605`，位于 `#[cfg(windows)]` 测试内，导入却没有
同样的条件。**这是既有缺陷，不是实现方引入的**，也不是绕过门禁的借口。实现方停下来
请示而没有用 `allow` / 跳过 clippy / 调整执行顺序绕过，处理正确。

因此授权一个**有界例外**，范围严格限定为：

### 允许

在 `spikes/**` 与 `xtask/**` 中，**仅**为让代码在非 Windows 平台通过编译与 lint 而做的
**条件编译属性修正**。典型形态就是给导入或条目补上与其唯一使用点一致的 `cfg`：

```rust
#[cfg(windows)]
use super::validate_exact_permission_cwd;
```

### 禁止（违反即打回）

- 改任何测试的断言、期望值或被测语义；
- 删除、`#[ignore]` 或 `#[allow]` 掉任何测试或 lint；
- 修改生产脱敏逻辑、fixture、schema；
- 借这个口子做与「让它在非 Windows 上编译」无关的任何整理、重命名或重构；
- 扩大到 `crates/kaleido-proto/**`、`docs/PROTOCOL.md`、`docs/adr/**`、
  `schemas/**`、`tests/fixtures/**` —— 这些仍然是硬冻结。

### 交付要求

1. **逐条列出**每一处改动：文件、行号、改前、改后、以及「唯一使用点在哪里、
   为什么这个 cfg 与它一致」；
2. 冻结区哈希基线**重新建立**，并说明差异恰好等于上面列出的条目，不多不少；
3. 证明语义未变：改动前后 Windows 上 `cargo xtask ci` 均 exit 0，
   且测试数量与通过数不变。

### 先把它们一次找齐，不要一次 CI 一个

主管实测：本机已安装 `aarch64-linux-android` 目标，它的 `cfg(windows)` 为假，
因此能在**本地**复现 macOS / Ubuntu 的同类失败：

```bash
cargo clippy --all-targets --target aarch64-linux-android -p kaleido-core -p kaleido-proto -p kaleido-state -p kaleido-adapter
```

`spikes/kaleido-recorder` 与 `xtask` 因为间接依赖 `ring` / `aws-lc-sys` / `blake3`
需要 C 交叉工具链，本机跑不通——那两个包只能靠 CI 验证。但至少纯 Rust 的部分可以先
在本地扫干净，避免每修一处就等一轮 CI。

### 附带授权：修 `platform/mod.rs` 的缺省分支（D-B4）

主管用上述方法扫描时发现了**另一处实现方尚不知道的问题**，同样属于跨平台构建，
一并授权在本卡修掉：

`crates/kaleido-adapter-codex/src/platform/mod.rs` 只枚举了 linux / macos / windows
三个 `target_os`，**没有缺省分支**。在任何第四种目标上：

```text
error[E0308]: mismatched types
  --> crates/kaleido-adapter-codex/src/platform/mod.rs:20:52
     expected `Result<(), Error>`, found `()`
warning: unused variable: `command`
```

这不影响当前 macOS / Ubuntu CI（三个分支各自命中），但 **`target_os = "android"` 不等于
`"linux"`**，所以这段代码在 R3 的目标平台上根本不编译。修法是给两个函数补一个诚实的
缺省分支——**不要**假装成功：`terminate_tree` 在不支持的平台上应返回明确的
`io::Error`，`configure` 可以是空实现但要让参数名不触发 warning。

（已确认 `kaleido-core` 本身对 `aarch64-linux-android` 编译通过，
所以这条不阻塞 T-102 的 UniFFI 结论。）

## 5.6 第三次授权：xtask 泄漏扫描器识别单前导反斜杠根（[ADR-0016](../adr/0016-recorder-out-of-ci-and-single-backslash-roots.md) D-2）

`xtask/src/fixtures.rs` 的 `absolute_path_candidates` 不识别 `\tmp\foo\secret.txt`
这种单前导反斜杠形态——而它在 Windows 上是合法的「当前驱动器根」绝对路径，
含该形态的 fixture 会整个绕过泄漏扫描。这是常驻门禁的真实缺口，不是 spike 问题。

允许在 `absolute_path_candidates` / `is_unc_absolute` 一线**增加**识别；
禁止改动 `path_is_inside_sandbox`、占位符抑制逻辑、任何断言、UNC 既有行为。

必须证明：新识别真的会咬（含改坏→变红）、真实 220 条记录三平台无误报、
sandbox 之内的单反斜杠路径不误报。

**这只增加候选形态识别，不回答 D-B6「`\` 在 Unix 上算不算分隔符」的语义问题。**

## 5.7 第四次授权：行尾确定性（[ADR-0017](../adr/0017-line-ending-determinism.md)）

干净 Windows checkout（`core.autocrlf=true`）下 `xtask/tests/deps.rs` 的精确 `.replace()`
静默未命中。生产依赖检查器是 CRLF 安全的（`lines()` + `trim()`），但主管核实到更深一层：
`xtask/src/schema.rs:874` 对**工作树字节**算 git blob SHA-1，因此干净 Windows clone 上
`cargo xtask schema diff` 会**假报 schema 漂移**，削弱 ADR-0012 D-2 的守卫（D-B10）。

授权：

- **D-1** 新增 `.gitattributes`：`* text=auto eol=lf`，并对 `schemas/**` 与
  `tests/fixtures/**` 用 `-text`（一手证据永不翻译）。必须确认这两个目录**内容字节未变**；
- **D-2** `xtask/tests/deps.rs` 的 setup 必须 **fail-loud**：断言替换确实发生了。
  仅规范化 CRLF 不够——静默无效的 setup 会让测试以错误的理由通过或失败。
  不许改业务断言或检查器语义。

## 7. 允许的结论包括「UniFFI 不够用」

如果回调、object 或 async 在两端任意一端行不通，**停下来按 `AGENTS.md` §5 报告**，
不要为了让它过而改 `kaleido-proto`，也不要自己发明一层影子 DTO。
主管会据此决定是改协议、改架构（例如移动端改用 `since_cursor` 轮询 + 本地
`kaleido-transport` 长连接），还是换绑定方案。
