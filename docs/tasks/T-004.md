## 目的

`AGENTS.md §2.3` 规定契约测试必须基于**真实录制的 JSONL**。这份 fixture 是所有 adapter 契约测试的地基，也是主管设计 `PROTOCOL.md` 的原始材料。

**UACP 的 12 个事件变体必须从三家真实报文推导出来，不能凭想象设计。** 因此这份录制的质量直接决定 G1 的质量。

本任务不写任何 adapter，只做两件事：**录**，和**证明录到的东西是真的、干净的、能被 schema 校验的**。

## 要求

### 1. 录制格式（固定，主管会照着写契约测试）

每行一条 JSON：

```json
{
  "ts_ms": 1420,
  "dir": "c2s",
  "transport": "stdio",
  "payload": { "...原始报文，一个字节都不许改..." }
}
```

- `ts_ms`：相对录制开始的毫秒数（**不是墙钟时间** —— 墙钟会让 fixture 每次 diff 都变化）
- `dir`：`c2s`（客户端→agent）或 `s2c`（agent→客户端）
- `transport`：`stdio` / `http` / `sse`
- `payload`：**原始报文原样保留**。不许重排键、不许美化、不许丢字段。脱敏是唯一允许的改动，且必须按第 3 节的规则可追踪

### 2. 必须录到的场景

每家 agent（Codex / Claude Code via ACP / OpenCode）都要录以下场景，各存为独立文件：

| 文件名 | 场景 | 目的 |
|---|---|---|
| `01-simple-turn.jsonl` | 一轮纯文本问答 | `TurnStart` / `MessageChunk` / `ThoughtChunk` / `TurnEnd` |
| `02-tool-call.jsonl` | 让它读一个文件并总结 | `ToolCallStart` / `ToolCallUpdate` / `ToolCallEnd` |
| `03-permission-approve.jsonl` | 触发一次需要审批的操作，**批准** | `PermissionRequest` + 批准后的继续 |
| `04-permission-deny.jsonl` | 同上，**拒绝** | 拒绝路径（错误路径，不许省） |
| `05-file-change.jsonl` | 让它改一个文件 | `DiffProduced` |
| `06-cancel.jsonl` | turn 进行中取消 | 中断语义 |
| `07-error.jsonl` | 让它跑一个必然失败的命令 | `Error` |
| `08-session-load.jsonl` | 用该 agent 自己的 CLI 建会话，再用协议列出并加载它 | ADR-0003 A-2 的证据 |
| `09-elicitation.jsonl` | 触发结构化表单输入（如 MCP OAuth） | `Elicitation`（ADR-0004 P-5） |

**关于 `09-elicitation.jsonl`**：这个可能触发不了。**触发不了是可以接受的，但必须交代清楚**：你试了什么方法、上游在什么条件下才会发这个请求、以及从 `schemas/` 里把该请求的 schema 定义摘出来贴在 `tests/fixtures/README.md` 里。**不许编造一份假的 elicitation 报文充数。**

**关于 `08-session-load.jsonl`**：录制方法是先用 `codex` / `claude` / `opencode` 各自的 CLI 手工建一个会话说一句话，然后用录制器走协议 `thread/list`+`thread/resume` / `session/list`+`session/load` / `GET /session` 把它列出来并加载。这份 fixture 是 ADR-0003 A-2 能否成立的直接证据。

### 3. 安全：脱敏与泄漏检测（对照 REQUIREMENTS §6.3）

**录制必须在 `tests/fixtures/sandbox/` 这个专用玩具项目里进行，绝不许在本仓库或任何真实项目里录。**

`cargo xtask fixtures verify` 必须扫描全部 fixture 并在命中时失败：

| 检测项 | 说明 |
|---|---|
| 当前用户名 | 从 `directories` / 环境变量取，出现即失败 |
| 家目录绝对路径 | `C:\Users\<name>`、`/home/<name>`、`/Users/<name>` |
| 疑似密钥 | `sk-`、`ghp_`、`Bearer `、`api_key`、`authorization` 头 |
| 沙盒外的绝对路径 | 路径必须都落在沙盒目录内 |

脱敏方式：把敏感串替换为稳定占位符（如 `<HOME>`、`<USER>`、`<REDACTED_TOKEN>`），**并在 `tests/fixtures/README.md` 记录替换规则**。替换必须是**确定性**的 —— 同一个原串在所有 fixture 里必须替换成同一个占位符，否则契约测试无法跨文件比对。

`tests/redact.rs` 必须验证：含用户名的报文被检出；含 `sk-` 的报文被检出；干净报文不被误报；替换的确定性（同输入同输出）。

### 4. Schema 校验

`cargo xtask fixtures verify` 还必须做：把每条 `payload` 按其方法名对照 `schemas/` 下的定义做 JSON Schema 校验。

**校验失败不一定是你的错** —— 也可能是上游 schema 与实际报文不一致。**这种情况极其重要，必须原样上报**（哪个方法、哪个字段、schema 说什么、实际发的什么）。这直接决定我们能不能信任自动生成的类型。**不要为了让校验通过而修改 fixture。**

### 5. 覆盖度报告

`tests/fixtures/README.md` 必须含一张表：**12 个 UACP 事件变体 × 3 家 agent**，标注每一格是「已录到（文件名 + 行号）」还是「未录到（原因）」。

这张表是主管设计 `PROTOCOL.md` 的直接输入。**空格子比假数据有价值得多** —— 未录到就如实写未录到。

## Windows 上的可执行文件解析（修订 R1 新增 —— 先读这节再判断环境）

> **修订 R1（2026-07-28）**：首次执行本卡时报告「`claude`/`opencode` 不可发现、`codex` 启动报
> `Access is denied`」并申请环境修复。经核对，**这与你自己在 T-003 交付的 `schemas/VERSIONS.md`
> 相矛盾** —— 那份文件明确记录了在同一环境下成功执行过：
>
> ```powershell
> codex.cmd app-server generate-json-schema --out schemas/codex
> opencode.cmd serve --pure --hostname 127.0.0.1 --port 4096 --log-level ERROR
> ```
>
> 也就是说 `codex` 与 `opencode` 是装好且能跑的，**只是不能用裸名字启动**。

这正是 `REQUIREMENTS.md §9` 的 **R-6**（Windows 上 npx/Node 子进程管理坑多）与
`AGENTS.md §3.5`（「Windows 特别注意：`npx` 实为 `npx.cmd`」）所指的陷阱。

**根因**：npm 全局安装在 Windows 上会生成三个文件 —— `codex`（**无扩展名的 POSIX sh 脚本**）、
`codex.cmd`、`codex.ps1`。从 Rust `Command::new("codex")` 直接 exec 那个无扩展名的 sh 脚本，
Windows 返回的就是 `Access is denied`。`claude` / `opencode` 「不可发现」是同一现象的另一面：
按裸名字查找时命中的不是可执行文件。

### 硬性要求

1. **不许用裸名字 spawn 外部 agent。** 必须做平台感知的可执行文件解析：
   Windows 上按 `PATHEXT` 顺序查找（`.cmd` / `.exe` / `.bat`），命中 `.cmd` 时按 Windows 的
   方式启动；非 Windows 直接用裸名字
2. 解析逻辑收敛在 `spikes/kaleido-recorder/src/platform/` 下（`AGENTS.md §3.5`）
3. 探测失败时，报告必须包含：**查了哪些候选名、每个候选的解析结果、以及 `where.exe <name>` 的原始输出**。
   只说「不可发现」信息量不足以判断是没装还是没解析对
4. 这段解析逻辑不是一次性代码 —— **hostd 将来 spawn 三家 agent 用的是同一套逻辑**，
   请当作会被复用的东西来写，并配单元测试

### 判定顺序

先按上面把解析修对，**再**判断环境是否真的缺东西。
如果修对解析后 `claude` 仍然找不到，那是真的没装，此时才按 `AGENTS.md §5` 报告阻塞 ——
但报告里要写清 `codex` 与 `opencode` 已经能跑、只有 `claude` 缺失，并**先把这两家的 fixture 录完**。

### 你找不到它们的原因是环境继承，不是安装（ADR-0006 D-8）

负责人的提示符是 `(base) PS C:\Users\Mumte>` —— 交互式 shell 加载了 conda 的 profile。
**shell profile 注入的 PATH 只存在于交互式会话里，被 spawn 出来的非交互进程拿不到。**

这不是本卡的调试细节，而是 hostd 的架构约束：hostd 会以托盘程序 / LaunchAgent /
systemd user unit 启动，**环境比你现在还贫瘠**，同样不会执行用户的 shell profile。
你在本卡写的发现逻辑，就是 hostd 将来要用的那套。

**因此发现必须多源**，按此优先级实现并逐层报告结果：

1. 显式配置（本卡用环境变量或 CLI 参数指定绝对路径即可）
2. 继承的 PATH（平台感知解析，Windows 按 `PATHEXT`）
3. 平台的持久化环境变量（Windows 用户 / 系统 PATH，**不是** shell profile 注入的那部分）
4. 已知安装位置（npm 全局 prefix、GUI 应用安装目录）
5. hostd 自备（仅 Claude Code 适用）

**探测报告必须逐层列出「在这 5 处分别看到了什么」**，并附上进程自身 `PATH` 环境变量的值。
「不可发现」这四个字信息量不足以定位问题。

### 关键事实：Claude Code 不需要用户装 CLI

`@anthropic-ai/claude-agent-sdk` 通过 npm **optionalDependencies 自带各平台的 Claude Code 原生二进制**
（`@anthropic-ai/claude-agent-sdk-win32-x64` 等）。官方文档原文：

> The SDK bundles a native Claude Code binary for your platform as an optional dependency…
> **You don't need to install Claude Code separately.**

因此本卡的 Claude Code 录制方式是：**用钉定版本的 `@agentclientprotocol/claude-agent-acp`，经 npm/npx 起 ACP 进程**。
这条路径不依赖用户环境，是首选。

用户的 `claude` CLI 确实存在（已实测），但它的作用是**逃生舱**与**录制 `08-session-load.jsonl` 的辅助**
（用它手工建一个会话，再用协议 `session/list` + `session/load` 把它读出来），
而不是起 ACP 进程的必要条件。

### 禁止的推断（ADR-0006 D-3）

**「PATH 上没有该 agent 的 CLI」⇒「该 agent 不可用」，这个推断一律打回。**

探测报告必须区分四种情况，不许笼统说「不可发现」：

1. 没装（三种来源都找不到）
2. 装了但解析方式不对（Windows `.cmd` / `PATHEXT`，见上一节 R-6）
3. **装了 GUI 但没装 CLI —— 此时多数 agent 仍然可用**
4. 装了但未登录

### 必须回答的问题（对应新增风险 R-11）

负责人的 Claude Code 是 **GUI 登录**的。本卡必须实测并给出结论：

> **GUI 写入 `~/.claude` 的登录态，能否被 npm 自备的 Claude Code 二进制直接复用？**
