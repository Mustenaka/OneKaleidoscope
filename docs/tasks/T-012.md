## 缺陷 1：同一个 bug 存在于两处，只修了一处

负责人执行 `cargo run -p xtask -- schema diff`：

```
schema: observed codex 0.146.0 (snapshot 0.146.0), opencode 1.18.9 (snapshot 1.18.8), acp 1.18.0 (snapshot 1.18.0)
schema: NOTICE opencode version differs: observed 1.18.9, snapshot 1.18.8; comparison will continue
schema: WARNING unverified version for opencode: observed 1.18.9, supported range =1.18.8; comparison will continue
schema: fetching Codex 0.146.0, OpenCode 1.18.9, ACP crate 1.3.0 / schema 1.18.0
xtask: schema I/O failure: could not terminate exact descendants of spawned root PID 124476: 拒绝访问。 (os error 5)
error: exit code 3
```

**前四行完全正确** —— ADR-0008 的版本模型工作了：版本不符只是 NOTICE/WARNING，比较继续进行。

**但随后死在了 T-009 已经修好的那个 bug 上。** `xtask/src/schema.rs` 有自己的一份
进程清理逻辑，没有应用 T-009 的「终止失败后重新快照确认，已消失即视为自然退出」。

### 要求

1. 把「进程树终止 + 重新快照确认」抽成**一份**实现，`xtask` 与 `kaleido-recorder` 共用
2. 抽取位置由你判断并说明理由；`docs/dependency-rules.toml` 需相应更新
3. 行为与 T-009 完全一致：终止失败 → 重新快照 → 已消失视为自然退出，仍存活才计入未确认
4. **`schema diff` 的清理失败不得让整个比较失败** —— 同 T-009 的解耦原则：
   比较结果已经拿到就该输出，清理不完整降级为警告

### 关于 M3 的收敛

`ARCHITECTURE.md` §6 规定进程监管最终收敛在 `crates/kaleido-adapter/src/platform/`。
`crates/` 要到 M3 才建，所以本卡的抽取位置是**过渡方案**。
请在 `docs/DEVELOPMENT.md` 记一条「M3 建 `kaleido-adapter` 时把它迁进 `platform/`」。
**不要在代码里写 `TODO`**（`AGENTS.md §2.4`）。

### 测试

- 复用 T-009 的四条断言，覆盖新的共用实现
- `schema diff` 在「比较成功 + 清理失败」时**仍输出比较结果**且退出码反映比较结论（0/1），
  不是 3
- 把这条改坏（清理失败即 I/O 错误），测试必须变红

## 缺陷 2：OpenCode 的录制判据用错了完成信号

```
kaleido-recorder: OpenCode fixture project root: .git=recorder-created; cleanup=RAII
kaleido-recorder: scenario was attempted but not recorded: OpenCode recorded 140 events
  but required evidence was absent: the prompt POST timed out before its sandbox session
  response could be validated;
  observations=["session.status.busy", "message.updated.assistant",
   "message.part.tool.started", "message.part.tool.updated",
   "message.part.tool.completed.correlated", "message.part.text",
   "session.status.idle", "session.idle"]
```

T-010 的 `.git` 自动生命周期**工作正常**。问题有两处：

### 2a. `POST /session/:id/message` 是长轮询，不该拿它当完成判据

SSE 侧 140 个事件里，完整生命周期全都到齐了
（`tool.started` → `tool.updated` → `tool.completed.correlated` → `text` → `idle`）。
唯独 POST 本身没在窗口内返回 —— 因为它要等整个 turn 结束才响应。

**要求**：完成判据改为 **SSE 生命周期**（`session.idle` / `session.status.idle` 到达
且 tool lifecycle 完整），POST 的返回值不再作为必需证据。

另外 OpenCode 提供 `POST /session/:id/prompt_async`（见 `schemas/opencode/openapi.json`）。
**优先评估改用它**，若可行就用；不可行则说明原因并沿用 `POST /message` + SSE 判据。

### 2b. 沙箱 session 的权限被配成了自动放行，所以根本没有审批可录

observations 里 tool 直接 `started → updated → completed`，**全程没有任何 permission 事件**。

线索在既有 fixture `tests/fixtures/opencode/08-session-load.jsonl:2`：

```json
"permission":[{"permission":"question","pattern":"*","action":"deny"},
              {"permission":"plan_enter","pattern":"*","action":"deny"},
              {"permission":"plan_exit","pattern":"*","action":"deny"}]
```

这些是 `deny`（直接拒绝），不是 `ask`（询问用户）。**只有 `ask` 才会产生权限请求。**

**要求**：录制 `permission-approve` / `permission-deny` 时，把沙箱 session 中
与目标操作相关的 permission 配成会触发询问的取值，让 OpenCode 真的发出权限请求。

具体取值请**从 `schemas/opencode/openapi.json` 里查证**，不要猜。
查到之后在 `tests/fixtures/README.md` 记录：哪个 permission 键、取什么值、为什么。

如果查证后确认 OpenCode 在当前版本下**没有**会产生权限请求的配置，
那本身就是一个必须上报的发现（意味着 OpenCode 的 `PermissionRequest` 在 v1 无法覆盖）,
按 `AGENTS.md §5` 报告，不要编造。

### 测试

- SSE 生命周期完整但 POST 未返回 → **判定为成功**，fixture 被安装
- SSE 生命周期不完整 → 仍然拒绝（**判据未被放宽**，要有测试证明）
- 把 2a 的修复改坏（恢复成「POST 必须返回」），第一条测试必须变红
