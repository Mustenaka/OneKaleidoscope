## 背景与唯一目的

REQUIREMENTS §9 的 **R-1 是本项目最高风险项**：如果 iroh 在运营商级 NAT（CGNAT）下打洞成功率过低，整个「P2P 直连」的产品假设就不成立，L2 relay 会从「可选组件」变成「v1 必做组件」，架构随之改变。

G0 的判定规则是硬性的：

> 在「家宽 hostd ↔ 4G 手机网络」下测 20 次，**直连成功率 < 60% 则 L2 relay 提升为 v1 必做项**。

因此本任务的产物是**一个能产出可信数字的测量工具**，不是产品代码。它是一次性的 spike，不进入 `crates/`，之后可能整体删除。

判断你是否做对的标准只有一个：**人类拿着这个工具跑 20 轮，能得到一个可以直接写进 `docs/gates/G0-result.md` 的百分比。**

### G0 的实测拓扑（已定，据此决定构建目标）

```
[ Windows PC · 家宽 ]  --- listen 侧，运行 x86_64-pc-windows-msvc 构建
        ↕  公网
[ Android 手机 · 4G ]  --- dial 侧，运行 aarch64-linux-android 构建（adb push 进 Termux）
```

因此 **Android 交叉编译是本任务的硬性交付项，不是可选项**（见 `docs/adr/0002-android-first.md`）。手机必须走 4G/5G 蜂窝网络，**不能连家里的 WiFi** —— 连 WiFi 就变成了同网段测试，测不到 CGNAT。

## CLI 契约（逐字实现）

我会照着这份契约写人工测试指引发给人类。**子命令名、参数名、stdout 前缀、exit code 都不许改**。

### `spike-iroh listen [--out <path>] [--label <str>]`

- 启动 iroh Endpoint，使用默认 relay 模式（**不要禁用 relay** —— iroh 先经 relay 建连再升级到直连，禁用 relay 会让测量失去意义）
- 在 stdout 打印**恰好一行**：`TICKET <base64url-no-pad>`，其中 payload 是 `EndpointAddr` 的 JSON 序列化
- 持续运行，接受多次连接；每个连接独立跑一轮 probe，各写一条记录
- Ctrl-C 优雅退出

### `spike-iroh dial <TICKET> --label <str> [--window-secs 30] [--out <path>]`

- `--label` 必填，用于区分测试场景（例：`lan`、`4g`、`4g-tether`）
- 连接后在观测窗口（默认 30s）内每 500ms 发一个 ping（序号 + 单调时钟时间戳），对端回 pong
- **全程观测路径变化**，记录：
  - 首次出现直连（IP）路径的时刻
  - 直连路径首次被**选中**（selected）的时刻 —— 这两个是不同的事件，都要记
  - 窗口结束时被选中的路径类型
- 窗口结束后写一条 JSONL 记录，并在 stdout 打印人类可读摘要
- **exit code 是测试协议的一部分**：
  - `0` = 连接成功且窗口结束时走直连
  - `10` = 连接成功但窗口结束时仍走 relay
  - `20` = 连接失败 / ticket 无效 / 其他错误

### `spike-iroh summarize <results.jsonl>`

按 `label` 分组输出，格式固定：

```
label=4g   runs=20  connect_ok=20  direct=13 (65.0%)  relay_only=7  median_time_to_direct=2.91s
label=lan  runs=5   connect_ok=5   direct=5 (100.0%)  relay_only=0  median_time_to_direct=0.34s
```

末尾必须打印 G0 判定行（只针对 `--label` 以 `4g` 开头的分组）：

```
G0 VERDICT: direct rate 65.0% >= 60.0% -> L2 relay stays OPTIONAL
```
或
```
G0 VERDICT: direct rate 45.0% < 60.0% -> L2 relay becomes MANDATORY for v1
```

## 记录 schema（字段名固定，我会逐字段审）

每行一条 JSON：

```json
{
  "schema": 1,
  "run_id": "b0f2...",
  "started_at": "2026-07-28T09:12:44Z",
  "role": "dial",
  "label": "4g",
  "iroh_version": "1.0.3",
  "os": "android",
  "remote_endpoint_id": "k51q...",
  "connect_ok": true,
  "connect_ms": 812,
  "direct_path_opened_ms": 3120,
  "direct_path_selected_ms": 3450,
  "ended_direct": true,
  "selected_path_at_end": "ip",
  "relay_url": "https://euw1-1.relay.iroh.network./",
  "local_direct_addrs": ["192.168.1.7:41641", "203.0.113.9:41641"],
  "rtt_relay_ms": 78.2,
  "rtt_direct_ms": 41.5,
  "pings_sent": 60,
  "pongs_recv": 60,
  "window_secs": 30,
  "error": null
}
```

- 连接失败时：`connect_ok=false`，`error` 填错误变体名 + 简短描述，其余时间字段为 `null`
- 未达成直连时：`direct_path_opened_ms` / `direct_path_selected_ms` / `rtt_direct_ms` 为 `null`，`ended_direct=false`
- **`listen` 侧也要写记录**（`role: "listen"`），字段相同 —— 因为 4G 侧设备取文件可能不方便，PC 侧的镜像记录是保险
- 记录里**不许**出现：用户名、主目录路径、机器名。本机 IP 是本 spike 的必要测量数据，允许保留

## 硬性约束

1. **iroh 版本**：必须用 1.0.x（撰写本卡时最新为 1.0.3）。**0.x 的 API 全部作废**，包括 `NodeId`、`NodeAddr`、`conn_type()`、`iroh-net` crate。训练数据里绝大多数 iroh 示例是 0.x 的，直接照抄一定编译不过。
2. **已确认存在的 1.0 API**（我已核对 docs.rs，可以直接用）：
   - `iroh::Endpoint::builder(presets::N0)` / `Endpoint::bind(presets::N0)`
   - `EndpointId`（原 NodeId）、`EndpointAddr`（原 NodeAddr）
   - `endpoint.connect(addr, ALPN)`、`endpoint.accept()`
   - `Connection::paths() -> PathList`、`Connection::paths_stream()`、`Connection::path_events()`
   - `Path::is_ip()`、`Path::is_relay()`、`Path::is_selected()`、`Path::remote_addr()`、`Path::rtt()`、`Path::stats()`
   - 注意：`Path` 借用自 `PathList`/`Connection`，**不能跨 task 边界**，需要带走的数据先 clone
3. **若实际 API 与上面列的不符**：停下来按 `AGENTS.md §5` 报告，**不许自己发明等价物、不许降级到轮询猜测**。
4. 局域网 mDNS 发现**不在本任务范围**（它在独立的 `iroh-mdns-address-lookup` crate 里，留给后续任务）。LAN 场景用同一套 ticket 流程测即可。
5. 错误类型用 `thiserror` 定义在 `error.rs`；`main.rs` 顶层可以用 `anyhow`。
6. 非测试、非 `main` 启动期代码中禁止 `unwrap()` / `expect()`。
7. 日志用 `tracing`，默认 `info`，支持 `RUST_LOG` 覆盖。
8. 新增依赖需在交付说明里逐个给出理由。

## 测试要求（这一节会被重点查）

`AGENTS.md §2.3` 适用：每个测试都必须**能够失败**。提交前自检：把实现改坏，它会变红吗？

### 必须有的测试

**1. `tests/loopback.rs` —— 端到端冒烟（能失败的真测试）**
- 同进程内起 listener 与 dialer，走 loopback 完成一轮短窗口（2s）probe
- 断言：`connect_ok == true`；`pings_sent == pongs_recv` 且 > 0；记录被写入指定文件且能被解析回来；`selected_path_at_end` 非空

**2. `tests/record_stats.rs` —— 统计与判定逻辑**
- 构造 3 条记录（2 条 direct、1 条 relay-only，label=`4g`）→ summarize 必须算出 `66.7%` 且判定为 `>= 60.0% -> ... OPTIONAL`
- 构造 5 条记录（2 条 direct）→ 必须算出 `40.0%` 且判定为 `< 60.0% -> ... MANDATORY`
- **边界值必须单独测**：构造 10 条记录恰好 6 条 direct（60.0%）→ 判定必须是 **OPTIONAL**（`>=` 而非 `>`）
- 多 label 混合时，G0 判定行只统计 `4g*` 分组
- `median_time_to_direct` 在偶数个样本时的取值规则要有测试（自己定规则，写进 README，测试锁死它）

**3. `tests/error_paths.rs` —— 至少 3 条错误路径**
- `dial` 一个语法非法的 ticket（比如 `"not-base64!!"`）→ 返回具体错误变体，进程 exit code `20`，**不 panic**
- `dial` 一个语法合法但对端不存在的 EndpointId（随机生成的公钥）→ 在超时内失败，且**仍然写出一条 `connect_ok=false` 的记录**（失败样本也是 G0 的数据）
- `summarize` 读到含损坏行的 JSONL → 跳过该行、在 stderr 报出行号、继续统计其余行，不 panic 也不静默吞掉

### 禁止

- `#[ignore]` 一律不许用，包括「这个测试要联网所以先 ignore」—— 需要网络的场景只允许走 loopback
- `assert!(true)`、空 body、只测 happy path
