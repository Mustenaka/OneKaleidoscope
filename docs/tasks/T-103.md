# T-103: 让 `AttentionState::Answered` 能表达「观察到的外部应答」（P-1）

> 状态：**实现与本地门禁完成，等待三平台 CI（2026-08-09）**。
> 里程碑：[MILESTONES](../MILESTONES.md) R3
>
> 本轮由用户以项目主管身份明确批准直接实施。P-1 按已接受的
> [ADR-0018](../adr/0018-attention-answer-provenance.md) 在同一变更中同步更新合同、proto、
> reducer、store 与测试。下文保留原问题分析，验收状态以 §4 为准。

一句话目标：消除 canonical 状态里一个**指不到任何命令**的 `CommandId` 引用。

---

## 1. 问题

[PROTOCOL](../PROTOCOL.md) §4.7 的 `AttentionState::Answered` 强制携带 `command_id`：

```rust
Answered {
    option_id: Option<String>,
    free_form_ref: Option<ContentRef>,
    decided_at_ms: i64,
    command_id: CommandId,      // ← 强制
}
```

这在「手机发命令 → broker 应答审批」的路径上是对的。但有第二条真实路径：
**Broker 观察到一个它没有发出的应答**。T-100 的 replay 就是这种情况——决定来自**被录制的
客户端**，本地从来没有过对应的 `CommandEnvelope`。

现在的实现（`crates/kaleido-adapter-codex/src/reduce.rs`）铸了一个确定性 ID 顶上，
并在注释里写明了。阶段 A 评审时主管接受了这个权宜之计，同时登记为 **P-1**。

**为什么必须在 R3 前解决**：手机会按 `command_id` 回查是谁做的决定、什么时候做的。
一个指向不存在命令的 ID，在 R3 会变成 UI 上的空洞或错误。而且这类「铸一个 ID 顶上」
的做法一旦形成先例，会扩散到其他字段。

这条路径不是只有 replay 会走。R5 接入 `shared_runtime` 模式后，
原生 CLI/GUI 在同一个 server 上做出的决定，Broker 也只能观察到。

## 3. 产出

### 3.1 先写 ADR（`docs/adr/0018-*.md`）

在改任何代码之前，先提出方案并说明：

- `Answered` 要如何区分「本地命令应答」与「观察到的外部应答」；
- 观察到的应答要携带什么证据（谁观察到的、什么时候、来源是什么）；
- 为什么不复用 / 复用 `CapabilityEvidence` 的 `EvidenceSource`；
- 对 `AttentionItem::check_reply` 的影响：观察到的应答是否还能被本地再回复一次
  （提示：不能，但错误码要选对）；
- 对已有 durable log 的影响。R2 已经产出过真实日志，
  **明确说明旧记录怎么处理**——协议还在 `0.1.x`，可以选择不兼容，但必须写清楚。

**ADR 写完先交给主管，等批准再动代码。** 这是本卡与前面几张卡最大的不同。

### 3.2 改协议与 proto

ADR 批准后：`docs/PROTOCOL.md` §4.7 与 `crates/kaleido-proto/src/attention.rs` 同步修改，
**文档先于代码**。字段名逐字一致。

### 3.3 改 adapter

`crates/kaleido-adapter-codex/src/reduce.rs` **删掉铸造 ID 的那段**，
改用新的表达。live 模式对合成 effect 的抑制逻辑是否还需要，一并重新评估
（提示：新表达可能让抑制变得不必要——如果是，就删掉它，并说明理由）。
