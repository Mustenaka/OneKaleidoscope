## 缺陷 1（主因）：清理失败不该作废已完成的录制

T-006 引入了严格的 PID-family 清理，并且在无法证明整树清理成功时**拒绝安装 fixture**。
这个方向是对的（主管要求过「不许把只杀了根进程报告为整树清理成功」），**但耦合错了**。

**录制的有效性取决于协议 transcript 本身，不取决于我们有没有收干净每一个孙进程。**
这两件事必须解耦：

| 关注点 | 正确处置 |
|---|---|
| 协议 transcript 完整、满足场景判据 | **fixture 有效，必须安装** |
| 进程树未能证明完全清理 | **警告**，写进录制元数据，**不作废 fixture** |

### 要求

1. 清理失败降级为**警告**，不再中止流程、不再拒绝安装 fixture
2. 在该次录制的元数据中记录：`cleanup: "incomplete"` + 未能确认终止的 PID 列表 + 原始错误
3. 退出码：录制成功但清理不完整 → **0**，并在 stderr 打印醒目警告
4. **只有 transcript 本身不合格才作废 fixture** —— 这条判据不许放宽

> 这条同样适用于 hostd（`ARCHITECTURE.md` §6）：
> hostd 绝不能因为收不干净一个孙进程就把用户的整个会话判为失败。

## 缺陷 2：`拒绝访问 (os error 5)` 被当成硬错误

Windows 上枚举后代 PID 后再 `OpenProcess`，若该进程**在两步之间已经退出**，
系统返回的往往是 `ERROR_ACCESS_DENIED (5)` 而不是「不存在」——
PID 可能已被回收并指向了另一个不属于当前用户的进程。

`codex.CMD` 的启动链是 `cmd.exe /D /S /C` → `codex.exe` → 可能还有孙进程，
这些短命进程在清理时早已自然退出，属于**正常情况**，不是故障。

### 要求

对每个终止失败的后代：**重新做一次 Toolhelp32 快照确认它是否还在**。

- 已不在快照中 → 判定为「已自然退出」，**不算失败**
- 仍在快照中且仍无法终止 → 才计入「未能确认终止」，走缺陷 1 的警告路径

**不要用 sleep + 重试来掩盖**，要用「重新快照确认」这种能给出确定答案的方式。
