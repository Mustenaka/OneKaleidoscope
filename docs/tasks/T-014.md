## 契约

```rust
pub fn apply(state: SessionState, event: ProviderEvent)
    -> Result<(SessionState, Vec<Projection>), ReduceError>;
```

**纯函数。无 IO、无网络、无 `tokio`、无时钟、无随机、无全局状态。同输入必同输出。**

## 状态模型

字段名可微调，**结构不许改**：

```
SessionState { session_id, cwd, status: Idle|Busy|Error, turns: Vec<Turn> }

Turn { id, status: Running|Completed|Failed|Cancelled,
       items: Vec<ItemId>, started_at, completed_at, error }

Item { id,
       kind: AgentMessage | Reasoning | Command | FileChange | Plan | Other(String),
       status: Pending | InProgress | AwaitingApproval
              | Completed | Declined | Failed | Cancelled,
       payload,
       approval: Option<Approval> }

Approval { request_id, requested_at, decision: Option<Decision>, decided_at }
```

## 硬性要求，每条都直接来自真实 fixture

### R-1 审批必须 join 到 Item 上

`item/fileChange/requestApproval` 的 params 只有 `threadId` / `turnId` / `itemId` /
`startedAtMs`，`reason` 与 `grantRoot` 都是 `null`，**不含任何可展示内容**
（`03-permission-approve.jsonl:50`）。

reducer 收到审批请求时必须按 `itemId` join 到已有 Item，并把该 Item 置为 `AwaitingApproval`。

**join 不到时必须返回明确错误，不许静默丢弃** —— 那意味着手机上会出现一张没有内容的审批卡。

### R-2 `decline` 绝不是错误

`04-permission-deny.jsonl` 逐字证明：`{"decision":"decline"}` 之后
`item.status` 变成 `"declined"`，而 **`turn.status` 仍是 `completed`、`turn.error` 仍是 `null`**，
agent 自己发一条 `final_answer` 解释。

因此：`decline` → `Item.status = Declined`，**turn 保持 `Completed`、`error` 保持 `None`。
不许产生任何 Error 状态或 Error 投影。** 映射错了手机上会显示成红色故障，与事实相反。

### R-3 文件内容不许进投影

`item.changes[].diff` 携带真实文件内容。Projection 里只允许**内容引用**
（哈希 + 字节数 + 路径），不许出现内容本身。依据 `REQUIREMENTS.md §6.3`。

reducer 不负责存储，只负责不把内容放进投影。

### R-4 基础设施 chatter 不产生投影

`mcpServer/startupStatus/updated` 在 `01-simple-turn.jsonl` 的 39 条里占 15 条。
`remoteControl/status/changed` 每个会话都会来一条。这类不产生任何 Projection，
但**要计数且可查询**（诊断需要）。

### R-5 未知方法走兜底，绝不 panic

Codex `0.144.6 → 0.146.0` 改了 2380 处。未知方法必须走
`Item.kind = Other(String)` / 无投影的路径。**禁止 `unwrap()` / `expect()` / panic。**

### R-6 只实现 fixture 证明过的语义

我们已核实 `schemas/codex/` 0.146.0 中存在 `turn/steer` / `turn/plan/updated` /
`turn/diff/updated` / `thread/loaded/list`，但**这三份 fixture 里没有它们的报文**。

**因此本卡不实现它们的语义**，全部走 R-5 的兜底路径。
在 `crates/kaleido-reducer-codex/README.md` 列一张「待 fixture」表说明原因。

**严禁根据 schema 自行编造这些事件的语义并写进 `tests/fixtures/`。**
（`AGENTS.md §2.3`：契约测试必须用真实录制的 fixture。）

## 测试

正确性完全由已有 fixture 判定：

1. **三条回放测试**：读入对应 JSONL，逐条 `apply`，断言最终 `SessionState` 与 Projection 序列
2. **03 vs 04 对比测试**：两者的最终 SessionState 除
   `item.status`（`Completed` vs `Declined`）与 `approval.decision` 外**必须完全一致**
3. **审批 join 失败** → 明确错误，不 panic
4. **内容不泄漏**：把全部 Projection 序列化后扫描，断言不含 fixture 里那段
   `KALEIDO PERMISSION PROBE`
5. **未知方法**不 panic，落到 `Other`
6. **纯函数性**：同一 `(state, event)` 连续 apply 两次结果一致
